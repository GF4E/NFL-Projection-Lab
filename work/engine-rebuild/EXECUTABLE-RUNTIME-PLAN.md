# Complete pipeline/runtime restoration before control activation

The September 23 readiness check locates the remaining recovery boundary: scorer capsules and same-runtime preparation/refit rollback are qualified, but they do not restore the complete preparation/publication executable and native environment. This is the next implementation task after the bounded storage profile; no activation follows from this plan.

1. Pin a committed source snapshot and installed environment, including interpreter, shared libraries, packages, symlinks and permissions. Keep runtime/source archives and raw manifests private on already approved storage. Record byte budgets before copying; no new provider, host, volume or retention change. The existing verified off-host repository recovery point remains retained.
2. Create a standalone source recovery point with Git history sufficient for the existing code-identity checks. Restore it and the runtime into new private directories, preserving actual absolute-prefix semantics. Do not copy credentials or mutable live ownership/lock state into an activated process.
3. On Linux, use a recursively private mount namespace to bind the restored runtime and checkout at their expected absolute paths only within the canary. The original host mounts must remain unchanged. Drop to the real service identity and deny outbound network access for the captured-input workflow. Namespace setup failure stops the canary; never fall back to running against live paths.
4. Reproduce existing forecasts and exercise the actual preparation/refit/release/lock/grade rollback workflow from restored code and interpreter. Simulated clocks/finals/publication remain labeled. Confirm unchanged original host locks, grades, active pointers and mounts outside the namespace. Preserve the restore receipt and all failure evidence.
5. Test corrupted/missing code/runtime members, unsafe links, incompatible fit/calibration/schema and interrupted recovery. A restored file tree is not success until the actual consumer reproduces expected output. Publish the bounded operator recovery procedure; do not imply automatic recovery for unsupported host-level failures.
6. Only then resolve the remaining training-migration review flags and qualify the checked production transition and exact served provenance. Update control authority from an actually qualified issuing path, never by relabeling a replay. E-CAL still requires its Tuesday registration, public closeout/refit and actual review rules.

Tier 1 conventions: existing fixed-prefix runtime semantics, isolated restoration, verified byte identities, existing service identity and private mount propagation learned from the completed storage migration. No model, parameter, metric, candidate, gate or population changes. Resource limits remain one worker/4 GiB; full-slate operation and phase ceilings remain unchanged and separately identified. Any genuinely undefined unsafe restore boundary is reported before dependent activation.
